3. LVGL event callback 구조 점검

화면 callback에서 buzzer 반응을 터치 직후로 당기기 위해 PRESSED와 CLICKED를 분리했다.

형태는 대략:

lv_event_code_t code = lv_event_get_code(e);

if(code == LV_EVENT_PRESSED)
{
    bk_printf(TAG "[TOUCH] PRESSED t=%lu\n",
              (unsigned long)lv_tick_get());

    hal_buzzer_beep();
    return;
}

if(code != LV_EVENT_CLICKED)
{
    return;
}

/* 실제 화면 전환 */

으로 정리했다.

목적은:

손가락 누름
 ↓
PRESSED
 ↓
즉시 beep

손가락 뗌 / click 판정
 ↓
CLICKED
 ↓
화면 전환

으로 만들어 사용자가 느끼는 입력 latency를 줄이는 것이었다.

LV_EVENT_ALL 등록 확인

기존 코드가:

lv_obj_add_event_cb(
    bk_ui->main_automode,
    main_automode_event_cb,
    LV_EVENT_ALL,
    NULL
);

형태였기 때문에 callback 자체가 여러 event에 진입한다.

따라서 callback 안에서:

if(code != LV_EVENT_CLICKED)
{
    return;
}

또는 PRESSED를 별도로 처리하는 방식은 정상이다.

오늘 중 event code 24, 27, 28, 29, 30, 31, 32, 33 등이 callback으로 들어오는 것도 확인했다.

중요한 점은 LV_EVENT_ALL이므로 CLICKED가 아닌 event가 들어오는 것 자체는 이상 현상이 아니라는 것이었다.

4. 오전 MemFault 추적

부팅/warmup 과정에서 발생하던 MemFault도 분석했다.

크래시 경로를 raw stack / ELF symbol을 이용해 복원한 결과 대략:

_uart_comm_task
    ↓
_boot_warmup_screens
    ↓
lv_obj_delete / lv_obj_del
    ↓
lv_obj_destructor
    ↓
lv_event_mark_deleted

쪽으로 이어졌다.

문제가 발생한 내부 상태는 LVGL event list 쪽이었다.

특히 당시 fault instruction은:

lv_event_mark_deleted
    ldr r2, [r3, #4]

계열이었고, event_head가 정상적인 LVGL RAM 영역이 아닌 이상한 주소를 가리키는 상태가 관찰됐다.

즉 단순히:

"lv_obj_del()이 children까지 지워서 죽었다"

수준의 문제가 아니라,

LVGL event/global 구조 자체가 오염됐거나 잘못된 object/event pointer를 타고 들어간 가능성이 주요 후보가 됐다.

ELF에서 lv_global도 확인했다.

2801db8c g O .bss 0000020c lv_global

즉 LVGL global state 자체가 .bss의 특정 영역에 존재하는 것도 확인했다.

이 작업을 통해 이후 screen lifecycle을 건드릴 때:

object delete
event callback
refresh
다른 task에서 LVGL 접근

이 동시에 얽히는 부분을 특히 조심해서 보기로 했다.

현재 주요 구조는:

같은 형태로 여러 페이지를 한 root 아래 두고 Z-order를 바꾸는 방식이다.

오늘 다시 확인한 중요한 점:

은 잘못된 값이 아니다.

LVGL에서 negative index는 뒤쪽부터 세는 방식이므로 -1은 마지막 child, 즉 foreground 쪽으로 보내는 용도로 정상이다.

move_to_index : 1 ms

에서 0, 1은 index 인자가 아니라 실행 시간이다.

따라서 화면 전환이 느린 이유는 move_to_index()가 아니다.

실제 비용:

move_to_index ≈ 0~1 ms
lv_refr_now   ≈ 1000 ms

였다.

7. Framebuffer 상태 확인

LCD는 1024×600, RGB565.

따라서 framebuffer 하나 크기는:

1024 × 600 × 2

이고 실제 로그도 framebuffer 두 개가 각각 해당 크기로 잡혀 있음을 확인했다.

즉 direct/double framebuffer 구성 자체는 정상적으로 보였다.

10. Dirty area가 작아도 JPEG 전체 decode

굉장히 중요한 발견.

dirty rectangle이:

60 × 60

정도로 아주 작아도 main.jpg가 약:

~350 ms

걸렸다.

또:

183 × 78
292 × 162

같은 작은 invalidation에서도 main.jpg 또는 manual_menu.jpg가 거의 원래 비용 그대로 발생했다.

즉 현재 JPEG pipeline은 clipping된 영역만 부분 decode하는 게 아니라 실질적으로:

작은 dirty region
       ↓
JPEG source 필요
       ↓
전체 JPEG decode
       ↓
필요 영역만 draw

에 가까운 동작을 한다.

그래서 작은 버튼 하나 invalidate해도 main.jpg 때문에 300ms 이상 잡아먹을 수 있다.

실제로 183×78 redraw에서도 main.jpg 하나가 359ms를 소비했다.

12. Hardware JPEG decoder 실험

BK7258의 HW JPEG decoder 경로도 검토했다.

Beken 쪽 HW JPEG decoder는 JPEG decode 자체를 hardware로 처리할 수 있지만 output이 YUYV 계열이라 이후 RGB 변환 등이 필요하다.

HW decode를 켰다고 생각되는 빌드에서도 실측 결과:

main.jpg        약 470~500 ms
manual_menu     약 310~330 ms
intro           약 350~420 ms

로 거의 변하지 않았다.

따라서 현재 가능한 해석은 두 가지다.

1. LVGL /images/*.jpg 경로가 실제 HW decoder를 안 타고 있음

또는

2. HW JPEG decode 자체는 빨라졌지만
file read
input staging
HW decode
YUV → RGB565
copy / blend
worker synchronization

전체 시간이 그대로라 IMG_TASK 기준으로 개선이 묻히고 있음.

그래서 이후 확인용으로 HW decoder entry에:

bk_printf("[JPEG_HW] decode start\n");

같은 직접 marker를 넣는 방법을 정리했다.

18. 오늘 가장 중요한 renderer 구조 발견

우리가 직접 child에:

lv_obj_send_event(
    child,
    LV_EVENT_COVER_CHECK,
    &child_info
);

를 보내니까 foreground automode가:

cover=0

으로 찍혔다.

하지만 이는 디버깅 코드가 직접 확인한 결과일 뿐이었다.

현재 확인한 lv_refr_get_top_obj()는:

static lv_obj_t * lv_refr_get_top_obj(
    const lv_area_t * area_p,
    lv_obj_t * obj)
{
    ...

    lv_obj_send_event(
        obj,
        LV_EVENT_COVER_CHECK,
        &info
    );

    if(info.res == LV_COVER_RES_MASKED)
        return NULL;

    if(info.res == LV_COVER_RES_COVER)
        return obj;

    return NULL;
}

형태다.

즉 우리가 보고 있는 코드에서는 넘겨받은 obj 하나의 COVER만 판단한다.

현재 obj == preRenderRoot이면:

preRenderRoot
bg_opa=0
cover=NOT_COVER

이므로 NULL을 반환한다.

반면 실제 foreground child의:

cover=COVER

결과는 top-object 반환 판단에 사용되지 않는다.

그래서 현재 동작이 사실상:

preRenderRoot
  └─ NOT_COVER
        ↓
top object 없음
        ↓
children 일반 traversal
        ↓
아래 sibling도 draw
        ↓
manual_menu.jpg decode
main.jpg decode
        ↓
마지막에 foreground automode가 덮음

처럼 보인다.

이게 오늘 renderer 쪽에서 가장 중요한 발견이다.

20. destroy_page_main() 타이밍 문제 발견

현재 callback 순서가:

lv_obj_move_to_index(target, -1);

lv_refr_now(NULL);

destroy_page_main(bk_ui);

이었다.

이 때문에 lv_refr_now() 시점에는 main이 아직 object tree 안에 살아 있다.

실제 로그:

main→automode
move_to_index
lv_refr_now called

manual_menu.jpg
main.jpg

lv_refr_now done

destroy_page_main called
destroyed

이다.

그래서:

"destroy_page_main() 하는데 왜 main.jpg를 decode하냐?"

의 답은 확실해졌다.

삭제하기 전에 refresh부터 하고 있기 때문이다.

21. main 삭제 후 또 redraw 발생

더 나쁜 점은 main을 삭제하면 LVGL이 해당 영역을 invalidate한다.

따라서 기존 흐름은:

1차 lv_refr_now
    ↓
manual + main 포함 렌더
    ≈ 1000 ms

destroy main
    ↓
화면 invalidate

2차 refresh
    ↓
manual 다시 decode
    ≈ 500 ms

가 된다.

실제로 main 삭제 직후:

manual_menu.jpg 321 ms
REFR_PERF      508 ms

가 다시 발생했다.

따라서 다음 구조가 훨씬 타당하다.

main 삭제
target foreground
        ↓
lv_refr_now 한 번

즉:

lv_obj_move_to_index(target, -1);

destroy_page_main(bk_ui);

lv_refr_now(NULL);

방향.

이 순서 변경은 아직 마지막 성능 로그에는 적용되지 않은 상태다.

        LV_OBJ_FLAG_HIDDEN)
    : (void)0;

bk_ui->autodrymode != NULL
    ? lv_obj_add_flag(
        bk_ui->autodrymode,
        LV_OBJ_FLAG_HIDDEN)
    : (void)0;

lv_obj_clear_flag(
    bk_ui->automode,
    LV_OBJ_FLAG_HIDDEN);

그런데 boot 중:

Assert at: lv_obj_add_flag:233

가 발생했다.

여기에는 여러 문제가 있었다.

문제 1. NULL만 검사함
ptr != NULL

이라고 해서 LVGL object가 아직 유효하다는 뜻은 아니다.

삭제된 pointer가 남아 있을 수도 있다.

따라서:

ptr != NULL &&
lv_obj_is_valid(ptr)

검사가 필요하다.

문제 2. automode는 검사 전에 API 호출

원래 코드가:

lv_obj_clear_flag(
    bk_ui->automode,
    LV_OBJ_FLAG_HIDDEN);

if(bk_ui->automode != NULL &&
   lv_obj_is_valid(bk_ui->automode))
{
    ...
}

순서였다.

즉 검사가 너무 늦다.

문제 3. init 함수가 화면 전환 함수처럼 변함

init_page_automode()는 부팅 warmup에서도 호출된다.

따라서 init 안에:

다른 페이지 숨기기
현재 페이지 표시
foreground 변경
refresh

같은 transition logic을 넣으면 boot/prewarm 과정과 runtime transition이 뒤섞인다.

그래서 page 생성과 page 활성화는 분리해야 한다는 결론.

24. LVGL task/context 문제도 재확인 필요

크래시 dump에서:

uart_comm
lvgl
swdraw
display_thread

등이 동시에 존재했다.

현재 UI 생성/warmup 일부가 _uart_comm_task 경로에 걸려 있기 때문에, LVGL object mutation을 어느 task에서 수행하고 있는지도 계속 주의해야 한다.

특히:

lv_obj_add_flag()
lv_obj_del()
lv_obj_move_to_index()
lv_refr_now()

등을 별도 RTOS task가 동시에 호출하면 LVGL object tree/event list와 renderer가 충돌할 가능성이 있다.

오늘 오전 MemFault와 오후 lv_obj_add_flag assert를 같이 보면 thread/context discipline은 앞으로 반드시 정리해야 할 항목이다.

0~1 ms

28. 현재 renderer에 대한 가설

현재 가장 강한 가설은:

preRenderRoot
    ↓
lv_refr_get_top_obj()
    ↓
preRenderRoot 자체 NOT_COVER
    ↓
top object 없음
    ↓
preRenderRoot 전체 child traversal
    ↓
아래 page image까지 decode
    ↓
마지막 foreground page가 최종적으로 덮음

이다.

즉 GPU식으로 생각하면:

보이지도 않을 layer들을 비싼 JPEG decode까지 다 한 뒤 마지막 layer로 덮는 상황.

그래서 현재 필요한 최적화는 JPEG를 480ms에서 300ms로 만드는 것보다, 애초에 안 보이는 JPEG를 decode하지 않는 것이다.

29. 다음 작업 우선순위
1순위 — destroy_page_main()을 refresh 앞으로 이동

현재:

lv_obj_move_to_index(target, -1);

lv_refr_now(NULL);

destroy_page_main(bk_ui);

를:

lv_obj_move_to_index(target, -1);

destroy_page_main(bk_ui);

lv_refr_now(NULL);

으로 바꿔서 테스트.

목표:

main.jpg decode 제거
두 번째 invalidate/redraw 제거

main 하나만 없어져도 약 480ms를 제거할 가능성이 있다.

2순위 — HIDDEN 실험은 init 함수 밖에서 수행

init_page_xxx()는 생성만 담당.

화면 callback에서만:

if(page != NULL &&
   lv_obj_is_valid(page))
{
    lv_obj_add_flag(
        page,
        LV_OBJ_FLAG_HIDDEN);
}

적용.

target만:

lv_obj_clear_flag(
    target,
    LV_OBJ_FLAG_HIDDEN);

처리.

그리고 반드시 refresh 직전 실제:

hidden=1

인지 로그로 확인.

3순위 — lv_refr_get_top_obj() 실제 호출 구조 확인

오늘 보여준 함수 단편만 보고 끝내지 말고:

grep -n -C 30 "lv_refr_get_top_obj" \
ap/components/lvgl/lvgl_v9/src/core/lv_refr.c

로:

caller
child recursion 존재 여부
top object 반환 후 draw 시작 위치
refr_obj_and_children() 또는 동등 함수와의 관계

를 정확히 확인해야 한다.

현재 fork에서 child recursion이 제거됐거나 다른 위치로 이동한 것인지 확인.

4순위 — lower sibling pruning 성공 후 image pipeline 최적화

그 다음 순서로:

JPEG HW decoder 실제 사용 여부
image cache
JPEG predecode
RGB565 native asset
PNG → RGB565 사전 변환
PSRAM decoded image cache

를 검토.

지금은 redundant draw가 남아 있기 때문에 decoder 자체만 최적화해도 근본적으로 낭비가 남는다.

30. 오늘 작업 한 줄 요약

오늘은 “LVGL 화면 전환이 왜 1초나 걸리는가”를 거의 renderer 내부까지 파고들어 추적했고, 병목이 framebuffer나 Z-order 변경 자체가 아니라 main.jpg + manual_menu.jpg 같은 보이지 않는 lower sibling 이미지의 반복 decode에 있다는 것을 확인했다. foreground page는 실제로 정상적으로 COVER 판정을 받지만 현재 refresh 경로에서는 그 결과가 lower sibling pruning으로 이어지지 않고 있으며, 동시에 destroy_page_main()이 refresh 뒤에 있어 main JPEG를 한 번 그린 뒤 삭제하고 다시 redraw하는 비효율도 확인했다. 다음 단계는 main 삭제 순서 변경과 inactive sibling의 실제 traversal 제거다.
